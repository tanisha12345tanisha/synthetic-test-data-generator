1. Purpose and document authority 

This document defines the complete Version 2 target for the Synthetic Test Data Generator. It consolidates the existing Version 1 baseline, the connected-tables proposal, and all decisions explicitly approved during scope definition. It is authoritative for requirements, architecture, security controls, data ownership, validation behavior, testing, deployment, and AI-assisted implementation. 

Rules for using this document as an AI prompt 

Never begin coding until the user explicitly approves the feature currently under discussion. 

Implement one feature at a time. Identify affected files first, request the current file contents, and return complete updated files ready to copy and paste. 

Preserve all existing Version 1 behavior and tests unless the approved requirement intentionally changes a contract. 

Never weaken, delete, skip, or rewrite a strict test merely to make implementation pass. Fix the source behavior or document a genuine approved contract change. 

Use no LLM, Ollama, external generative AI service, Kaggle dataset, downloaded dataset, or production data at runtime. 

All generated data must be synthetic. Database input is metadata-only. CSV input remains schema-inference-only. 

Maintain deterministic generation where the same normalized schema, configuration, relationships, and seed produce the same output. 

When suggesting implementation changes, always name the file and function/class. Do not provide partial file fragments when the user requests complete files. 

Requirement language 

MUST and SHALL indicate mandatory behavior. SHOULD indicates a strong default that may change only through an approved decision. MAY indicates optional behavior. DEFERRED means explicitly excluded from Version 2.

7. Authentication, session, and email requirements 

Registration 

Required fields: display name, email, password, confirm password. 

Normalize email for comparison and enforce uniqueness. 

Never store plaintext passwords. Use a modern adaptive password hash. 

Reject inactive/disabled accounts at login. 

Use generic authentication errors that do not reveal whether an email exists. 

Rate-limit registration and authentication endpoints. 

Record security-relevant events without logging passwords, tokens, or reset links. 

Session model 

Short-lived access token and refresh-token workflow. 

Refresh tokens are revocable and associated with user/session metadata. 

Logout revokes the current refresh token. Password reset revokes all active sessions. 

Protected frontend routes redirect unauthenticated users to login while preserving a safe return route. 

Backend authorization is always enforced independently of frontend visibility. 

Email password reset 

Forgot-password requests return the same response for existing and non-existing accounts. 

Generate long, cryptographically random, single-use reset tokens. Store only a secure token representation. 

Tokens expire after a configurable period and become invalid immediately after use. 

Rate-limit requests by relevant dimensions such as account and requester context. 

Reset form requires new password and confirmation. 

After reset, send a confirmation email and revoke existing sessions. 

Email copy never includes a password. Email links use the configured trusted frontend origin. 

Future SSO compatibility 

User identity records must support one or more identity providers so future company SSO can be linked to the existing application user without changing dataset ownership. Email/password remains the approved Version 2 method.

9. Dataset lifecycle, autosave, and versioning 

Dataset states 

Draft: editable and not yet generated. 

Ready: configuration passes validation. 

Generating: active generation exists. 

Available: output is retained and downloadable. 

Output expired: history exists but file is unavailable. 

Archived: hidden from ordinary lists but recoverable by owner/admin policy. 

Failed: latest generation failed with safe diagnostic information. 

Hybrid versioning 

Edits autosave to a mutable working draft. Autosave does not create permanent versions. 

Permanent versions are created when the user selects Save Version, starts generation, imports a schema, or restores an earlier version. 

Starting generation first validates the draft and creates an immutable snapshot used by that generation. 

Restoring older content creates a new current version referencing the source version. It never removes intervening history. 

A version snapshot contains tables, columns, relationships, rules, distributions, case settings, seed behavior, input mode, and relevant limits. 

Concurrent edit conflicts must be detected using revision/version checks rather than silently overwriting changes. 

10. Input modes and privacy boundaries 

Manual 

Users create one or more tables, columns, constraints, distributions, relationships, and rules directly in the application. 

CSV 

Single mode accepts one CSV; connected mode accepts multiple CSV files. 

Files are processed only to infer schema/configuration and candidate relationships. 

Original rows are not copied to output and are not retained after inference processing. 

The UI displays a clear notice instructing users to upload mock or sample files, not production data. 

All inferred results are editable and require user review before generation. 

Database metadata 

Supported connectors: PostgreSQL, MySQL, Microsoft SQL Server, and Oracle. 

Read metadata only: catalogs/schemas, tables, columns, native data types, nullability, defaults, primary keys, foreign keys, and supported uniqueness/check constraints. 

Do not issue row-reading SELECT queries against source business tables. Do not sample, profile, copy, or cache source values. 

Connection credentials must be read-only and never be returned in API responses or logs. 

Operations that mutate source databases are prohibited. 

The user selects included schemas/tables and reviews normalized metadata before saving. 

Database-specific types map into a common internal type model. Unmapped types are flagged for manual resolution. 

Schema JSON import/export 

Export contains only schema/configuration, never generated rows or database secrets. 

JSON includes a document format version for forward compatibility. 

Import validates structure, supported types, reserved names, limits, relationships, and rules before creating a permanent schema version. 

Unknown fields follow a defined compatibility policy and produce clear warnings/errors. 

Templates 

Templates may define single or connected schemas. 

Using a template creates an independent user-owned dataset. 

Administrators manage system templates and template versions. 

Templates contain no real or production records. 

11. Multi-table model and referential integrity 

Supported structures 

One-to-one. 

One-to-many. 

Many-to-many represented by an explicit junction table. 

Multi-level acyclic dependency chains. 

Multiple independent roots within one dataset are allowed if every component is valid. 

Deferred/blocked structures 

Circular dependency graphs. 

Self-referencing relationships. 

Composite foreign keys in initial Version 2 delivery. 

Implicit many-to-many relationships without a junction table. 

Relationship validation 

Referenced tables and columns must exist. 

Parent key must be primary or uniquely constrained. 

Parent and child key types must be compatible after normalization. 

Required child foreign keys cannot be nullable. 

A one-to-one child foreign key must be unique. 

Many-to-many junction tables contain valid foreign keys to both parents and may enforce pair uniqueness. 

Dependency graph must be acyclic. 

Every table must be reachable in a valid generation component. 

Relationship suggestions from CSV/database metadata are never silently accepted; users can accept, edit, or remove them. 

Generation algorithm contract 

Validate complete schema and limits. 

Create immutable schema version for the run. 

Build dependency graph and topological generation order. 

Initialize deterministic random state from approved seed behavior. 

Generate parent/root tables and validate primary-key uniqueness. 

Store generated parent keys in an in-memory run-scoped key registry. 

Generate child non-key fields using existing type and case engines. 

Assign valid child foreign keys from parent key registries according to cardinality and distribution rules. 

Generate junction-table key pairs without forbidden duplicates. 

Apply cross-column and derived rules in declared order. 

Apply negative cases without corrupting protected keys unless an explicitly selected relationship-negative case requires it. 

Run table-level quality validation. 

Run cross-table referential-integrity validation. 

Create reports and export artifacts. 

Persist run summary and temporary file reference, then schedule expiry. 

Relationship-aware negative cases 

Version 2 may deliberately generate invalid relationship scenarios only when the user selects them. Such rows must be clearly labeled and excluded from the pass expectation for ordinary integrity checks. Supported candidates include orphan foreign key, null required foreign key, duplicate primary key, invalid foreign-key format, one-to-one uniqueness violation, junction duplicate pair, and cardinality violation. Every injected violation must have case metadata and a report entry identifying intentional versus accidental invalidity. 

12. Cross-column rules and derived fields 

Rule model 

Rules are declarative configuration, not arbitrary Python, SQL, JavaScript, or shell code. 

Rules reference columns using stable identifiers or validated names. 

Rule evaluation order is explicit. 

Cycles between derived fields are detected and rejected. 

Type-check rule outputs before generation. 

Missing-source behavior is configurable where applicable: reject configuration, produce null, or use an approved fallback. 

Required rule families 

Type 

Examples 

Derivation 

full_name = first_name + last_name; total_amount = quantity * unit_price. 

Conditional 

status Active implies is_active true. 

Comparison 

end_date must be on or after start_date. 

Mapping 

country India implies currency INR. 

Aggregation-safe 

Line-level calculations only in initial release unless cross-row behavior is explicitly designed. 

Lookup within generated context 

Foreign key selection and parent-linked attributes from generated parent records. 

 

Safety 

The expression engine must use an allowlist of operators and functions. It must prohibit file access, network access, imports, reflection, process execution, database queries, and unbounded recursion. 

13. Generation jobs, retention, and outputs 

Background job states 

Queued, Validating, Generating, Validating Output, Packaging, Completed, Failed, Cancelled, Expired. 

Progress 

Persist high-level progress and current phase. 

Avoid false precision; report known phase progression and completed table counts. 

Allow safe retry from the same immutable schema version and seed. 

Prevent duplicate submissions through idempotency safeguards. 

Cancellation stops future work where practical and cleans partial artifacts. 

Temporary retention 

Generated rows are not stored in PostgreSQL. 

Artifacts are stored temporarily in Cloud Storage. 

The output record stores format, size, checksum, object reference, created time, expiry, and deletion status. 

The retention period is configurable by Admin. 

Users may delete outputs earlier. 

History remains after expiry and displays Output expired. 

Download authorization is checked every time; storage paths are never treated as authorization. 

Export structure 

Single table: CSV, PSV, JSON. 

Connected tables: ZIP with one file per table, relationship_manifest.json, relationship_report.json, quality_report.json, and a schema snapshot. 

Safe deterministic filenames, stable column ordering, and explicit encoding. 

Metadata columns remain included unless an approved export option changes this behavior.

- Inputs: manual, CSV, schema JSON, template, and database metadata. 

- Database connectors: PostgreSQL, MySQL, Microsoft SQL Server, and Oracle. Metadata only. No row reads, sampling, or mutations. 

- Multi-table relationships: one-to-one, one-to-many, and many-to-many through explicit junction tables; multilevel acyclic graphs. Circular, self-referencing, and initial composite foreign keys are excluded. 

- Configurable table count: default 5, admin maximum 20. Per-table and total-dataset row limits are separately configurable in Admin Portal. 

- Cross-column rules and derived fields use a safe allowlisted expression engine, never eval/exec or arbitrary code. 

- Background generation jobs, quality/integrity reports, generation history, schema templates, advanced search/filtering. 

- Users cannot create API keys. 

- Deploy on Google Cloud using Cloud Run, Cloud SQL for PostgreSQL, Cloud Storage, Secret Manager, Cloud Build, Logging/Monitoring, least-privilege IAM, and an approved configurable email provider. Prefer source-based deployment without a manually maintained Dockerfile. 

 

IMPLEMENTATION QUALITY 

- Enforce authorization in backend for every resource. 

- Use database constraints and application validation. 

- Use migrations and transactions. 

- Use safe, stable error codes and correlation IDs. 

- Protect primary and foreign keys from accidental negative-case mutation; explicitly labeled relationship-negative cases are handled separately. 

- Generate parent tables before child tables using topological ordering and run-scoped key registries. 

- Reports distinguish intentional negative cases from accidental failures. 

- Existing Version 1 tests must remain green. Add branch, integration, API, security, frontend, end-to-end, and performance tests appropriate to the feature.
